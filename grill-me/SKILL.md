# Grill Me — 无情对齐

源自 Matt Pocock `skills/productivity/grill-me` + `grilling`，改写为 Hermes 单技能版（原版分 user-invoked `grill-me` 与 model-invoked `grilling` 两层，这里合并为一个可直接触发的技能）。

> 核心理念：软件开发最常见的失败不是技术，是**没对齐**。先把用户拷问到每个设计分支都收敛，再动手。

## 何时触发
用户给出模糊指令、要做大改动、或显式说「聊聊/对齐/确认方案」。即使用户说「你定」，也要先把方向收敛到可执行的边界再执行——但**事实问题自己查，只把决策交给用户**。

## 流程

### 1. 建树
内部建一棵「设计树」：根 = 用户的目标；每个决策节点挂它依赖的子决策。不落盘，只在脑子里/草稿里维护。

### 2. 算 frontier
**frontier** = 所有前置依赖已确定的决策（现在就能问、不用猜还没听到的答案）。

### 3. 每轮发问
一轮内把整个 frontier 问完，格式：

```
❓ Q1 - <问题标题>：<问题正文，可多段，含选项>

➡️ <你的推荐答案>

---

❓ Q2 - <问题标题>：<...>

➡️ <你的推荐答案>
```

要求：
- 每条**必给推荐答案**（放第一个，UI 会高亮），用户可改。
- 选项写成可选列表，不要把选项塞进问题正文。
- 需要环境事实的 frontier 问题 → 派 sub-agent 去查，不阻塞其余问题；只等下游依赖。

### 4. 重算 frontier
用户答完 → 已定决策把 frontier 向外推，解锁被挡的问题；依赖本轮未决问题的归入下一轮。**不在本轮插问依赖未决的问题。**

### 5. 收口
frontier 为空 = 每个分支都访问过、无静默假设。此时**复述共识一句话**，等用户确认「对/可以」再行动。未确认前不执行任何改动。

## 边界
- 事实（版本、文件路径、接口）自己查，绝不反问用户。
- 决策（要什么、不要什么、优先级）交给用户，等答案。
- 拷问完成后**不自动动手**，必须用户确认共识。
