# Idea Refine

## Overview

"我不知道我要什么，但我看到就知道"——这是需求方常态。idea refine的任务是把模糊的描述变成明确的需求，再把需求变成可执行的方案。不是替需求方做决定，而是帮助他们看清选项并做出选择。

## When to Use

- 用户描述模糊，不知道具体要什么
- 同一需求有多种理解方式
- 需要在多个方案中选择
- 需求边界不清晰
- 技术方案需要评审对齐

## Process

### Phase 1: 理解原始想法

#### 1.1 完整倾听
- 不要打断，让对方说完
- 记录所有关键词
- 注意对方反复强调的部分

#### 1.2 澄清表面信息
- 什么场景触发这个需求？
- 期望的结果是什么样的？
- 优先级（必须 vs 想要 vs 可以不要）？

#### 1.3 识别隐含假设
- 对方默认了什么？
- 有什么先入为主的条件？
- 有没有不切实际的期望？

### Phase 2: 探索需求空间

#### 2.1 5Why追问法
```
用户：我想做一个商品比价功能
Q: 为什么需要这个功能？
A: 因为我想知道哪个平台价格最低
Q: 为什么想知道最低价？
A: 因为我想省钱
Q: 为什么要省钱？
A: 因为预算有限
Q: 预算是多少？
A: 每月XX元
Q: 那其实核心需求是：如何在固定预算内找到最合适的商品？
```

#### 2.2 约束挖掘
- 成本约束：预算多少？开发资源？
- 时间约束：什么时候要？
- 技术约束：什么平台？什么技术栈？
- 质量约束：什么标准算好？

#### 2.3 用户故事构建
```
作为 [用户角色]
我想要 [功能]
以便 [价值/收益]
验收标准：
- [具体可测试的标准1]
- [具体可测试的标准2]
```

### Phase 3: 方案探索

#### 3.1 多方案对比
- 不要只给一个方案
- 至少给出2-3个选项
- 每个方案说明：优点、缺点、适用范围、成本

#### 3.2 快速原型
- 用最简单的方式验证理解
- 可以是草图、原型图、文字描述
- 目的是验证，不是交付

#### 3.3 方案选择
- 帮助需求方理解各方案差异
- 不替需求方做决定
- 记录决策过程和理由

### Phase 4: 规格化

#### 4.1 编写需求规格
```
功能名称：[具体名称]
功能描述：[1-2句话]

用户场景：[谁在什么情况下使用]

功能需求：
1. [具体需求描述，可测试]
2. [具体需求描述，可测试]

非功能需求：
- 性能：[标准]
- 安全：[标准]
- 兼容性：[标准]

验收标准：
- [ ] [标准1]
- [ ] [标准2]
```

#### 4.2 评审与确认
- 和需求方逐条确认
- 和开发团队确认可行性
- 识别潜在风险和依赖

## Common Rationalizations

| 常见借口 | 真相 | 反制 |
|---------|------|------|
| "我大概知道需求了，可以开始做了" | 大概知道=不知道 | 必须有书面规格并确认 |
| "先做，做了再说" | 做了再改的成本是规格阶段修改的10倍 | 先花时间明确范围 |
| "需求很简单，不需要详细规格" | 越简单的需求越容易误解 | 用简单格式记录关键点 |
| "对方说不清楚，我也没办法" | 说不清楚是常态，要用引导技巧 | 用原型、例子、类比来引导 |
| "技术上怎么做我不管" | 技术约束会影响需求可行性 | 早期引入技术评审 |

## Red Flags

- 需求描述超过5分钟还没说清楚要什么
- 多次听到"大概"、"可能"、"应该"等模糊词
- 对方对技术方案有强烈偏好但不理解技术
- 需求范围在讨论中不断扩大
- 各方对需求的理解明显不一致
- 没有明确的验收标准
- 对方说"你先做一版看看"

## Verification

验证清单：

- [ ] 需求已用用户故事格式记录
- [ ] 需求方已确认规格文档
- [ ] 验收标准已定义且可测试
- [ ] 多个方案已对比
- [ ] 方案选择有明确理由
- [ ] 技术可行性已评估
- [ ] 风险和依赖已识别
- [ ] 优先级和范围已确认
