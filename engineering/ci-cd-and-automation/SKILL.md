# CI/CD and Automation

## Overview

CI/CD是代码质量的第一道防线和发布效率的核心杠杆。好的CI/CD让每次提交都能得到即时反馈，让发布变成一键操作。坏的CI/CD让开发者不信任自动化，花更多时间在手动操作上。

## When to Use

- 搭建新的CI/CD系统
- 优化现有的CI/CD流程
- 引入自动化测试
- 改进部署策略
- 解决CI/CD失败率高的问题

## Process

### Phase 1: CI设计

#### 1.1 选择CI工具
| 工具 | 适用场景 |
|------|---------|
| GitHub Actions | GitHub生态，免费额度大 |
| GitLab CI | GitLab用户 |
| Jenkins | 自托管，高度定制 |
| CircleCI | 快速，高并发 |
| Argo Workflows | Kubernetes原生 |

#### 1.2 CI流水线阶段
```
Push → Lint → Unit Test → Build → Integration Test → Report
```

#### 1.3 流水线配置原则
- **快速失败**：lint和单元测试在前，耗时的集成测试在后
- **并行执行**：无依赖的阶段并行，缩短总时间
- **缓存复用**：依赖安装、构建产物要缓存
- **幂等性**：任何阶段可以重跑而不改变结果

### Phase 2: 自动化测试

#### 2.1 测试金字塔
```
        /\
       /  \      E2E（少量）
      /----\
     /      \    Integration（适量）
    /--------\
   /          \  Unit（大量）
  /____________\

  数量：70% 单元 / 20% 集成 / 10% E2E
  成本：E2E > 集成 > 单元
  价值：E2E = 集成 = 单元（覆盖率相同情况下）
```

#### 2.2 测试覆盖率目标
- 核心业务逻辑：>80%
- 新功能：>90%
- Bug修复：必须有回归测试

#### 2.3 测试数据管理
- 测试数据工厂（Factory）
- 测试数据清理（每个测试后）
- 共享fixture vs 本地fixture

### Phase 3: CD设计

#### 3.1 部署策略
| 策略 | 适用场景 | 风险 |
|------|---------|------|
| 直接部署 | 低风险、快速迭代 | 回滚慢 |
| 蓝绿部署 | 中高风险，需要快速回滚 | 需要双倍资源 |
| 金丝雀 | 高风险，灰度验证 | 复杂度高 |
| Rolling | 有状态服务 | 需要兼容多版本 |

#### 3.2 环境管理
- Development：开发人员日常开发
- Staging：接近生产，用于最终验证
- Production：真实用户流量

#### 3.3 部署检查清单
- [ ] 数据库迁移兼容
- [ ] 配置变更兼容
- [ ] 回滚方案就绪
- [ ] 健康检查通过
- [ ] 监控告警就绪

### Phase 4: 流水线优化

#### 4.1 优化指标
- 构建时间：从提交到反馈的时间
- 失败率：流水线失败的比例
- 误报率：实际没问题的构建被标记失败

#### 4.2 常见优化
- 缓存依赖下载
- 增量构建（只构建变更部分）
- 测试用例并行
- Docker层缓存

#### 4.3 监控与告警
- 构建时间趋势
- 失败率趋势
- 特定提交/文件的失败模式

## Common Rationalizations

| 常见借口 | 真相 | 反制 |
|---------|------|------|
| "CI太慢，影响开发效率" | CI慢往往是没有优化 | 记录优化后节省的时间 |
| "测试可以手动跑，不需要自动化" | 手动测试不可靠且不能重复 | 强制CI必须通过才能合并 |
| "生产环境手动部署更可控" | 手动部署必然带来不一致 | 基础设施即代码，部署自动化 |
| "回滚太麻烦，不值得" | 回滚是最后防线，必须快速 | 蓝绿/金丝雀部署，回滚一键化 |

## Red Flags

- CI/CD没有自动化测试
- 流水线时间超过20分钟
- 失败率超过10%
- 没有缓存策略
- 部署是手动scp/ftp
- 环境之间有差异
- 没有回滚方案
- 提交代码后需要等待>1小时才能知道结果
