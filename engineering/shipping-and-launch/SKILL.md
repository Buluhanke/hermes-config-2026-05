# Shipping and Launch

## Overview

发布不是"git push"的那一刻，而是从准备阶段开始到监控验证结束的全流程。一次糟糕的发布可以毁掉数周的开发工作，一次好的发布让用户感受不到任何变化。

## When to Use

- 任何功能需要发布到生产环境
- 任何系统迁移或重大架构变更
- 任何涉及数据库变更的发布
- 任何涉及API接口变更的发布
- 任何涉及安全相关的发布

## Process

### Phase 1: 发布准备

#### 1.1 版本确认
- 确认语义化版本号
- 确认变更内容清单（changelog）
- 确认是否需要数据迁移
- 确认是否需要配置变更

#### 1.2 测试完成确认
- 单元测试覆盖率达标
- 集成测试通过
- 端到端测试通过
- 性能测试通过（如果有性能要求）
- 安全扫描通过

#### 1.3 依赖确认
- 第三方依赖版本兼容
- 数据库版本兼容
- 缓存版本兼容
- 基础设施兼容性

### Phase 2: 预发布检查

#### 2.1 部署到预生产环境
- 使用与生产相同的环境配置
- 运行完整的回归测试
- 验证数据迁移（如果有）
- 验证配置加载
- 验证监控和告警

#### 2.2 灰度策略
- 决定灰度发布策略
- 准备回滚方案
- 准备切流脚本
- 确认通知流程

#### 2.3 通知
- 通知相关团队（ops, SRE, 支持团队）
- 通知利益相关者
- 确认紧急联系人
- 确认回滚授权

### Phase 3: 部署执行

#### 3.1 部署步骤
- 记录每一步操作
- 监控部署进度
- 验证服务启动
- 验证健康检查

#### 3.2 切流
- 小流量切流（10%）
- 监控错误率和延迟
- 逐步放大流量
- 确认无异常后全量

#### 3.3 部署后验证
- 功能验证
- 端到端测试
- 监控仪表盘检查
- 日志检查

### Phase 4: 监控与应急

#### 4.1 发布后监控
- 错误率
- 延迟（P50/P95/P99）
- 流量变化
- 资源使用率

#### 4.2 问题发现
- 定义什么情况是"有问题"
- 准备快速检测方式
- 明确升级流程

#### 4.3 回滚
- 触发回滚的条件
- 回滚步骤
- 回滚后通知

### Phase 5: 完成后收尾

#### 5.1 验证发布
- 确认所有功能正常
- 确认监控正常
- 记录发布问题（如果有）

#### 5.2 文档更新
- 更新API文档
- 更新用户文档
- 更新运维文档
- 记录发布总结

#### 5.3 团队通知
- 通知发布完成
- 收集反馈
- 安排值班监控

## Common Rationalizations

| 常见借口 | 真相 | 反制 |
|---------|------|------|
| "测试环境没问题，生产也一样" | 测试环境和生产环境必然有差异 | 生产环境巡检必须做 |
| "这次改动很小，不需要完整测试" | 小改动往往带来大风险 | 小改动只跳过重复测试，核心测试必须做 |
| "发布会很短，先发布再说" | 发布后出问题往往在流量高峰 | 预留足够的监控时间窗口 |
| "监控没有异常，说明一切正常" | 有些问题不会立即体现在监控上 | 多维度验证，不只看监控 |
| "回滚太麻烦，修复比回滚快" | 如果连基本功能都挂了，必须先回滚 | 回滚优先，修复其次 |

## Red Flags

- 部署前没有检查清单
- 没有回滚方案就发布
- 没有监控就发布
- 跳过预生产直接上生产
- 部署时间在业务高峰期
- 部署后无人监控
- 多系统依赖但没有协调发布
