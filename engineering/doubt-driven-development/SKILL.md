# Doubt Driven Development

## Overview

好开发者不是因为知道所有答案，而是因为知道如何验证不确定性。面对不确定的情况，猜测是最低效的做法——用实验来验证假设才是正道。

## When to Use

- 两个技术方案各有优劣，无法决定
- 文档说X，但代码行为是Y
- 遇到"不应该发生"的bug
- 不确定某个API的具体行为
- 需要验证性能假设
- 交接时对方说的和你理解的不一致

## Process

### Phase 1: 明确不确定性

#### 1.1 识别核心问题
- 用一句话描述不确定的点
- 是什么让这个决定变得困难？
- 假设如果错了，最坏会发生什么？

#### 1.2 收集已知信息
- 文档说了什么？
- 代码实际做了什么？
- 测试说明了什么？
- 其他人的经验（issue/stackoverflow）？

#### 1.3 区分不同类型的不确定
- **事实型**：可以用实验验证（这个API的参数是什么）
- **经验型**：可以用他人经验回答（用A还是B好）
- **预测型**：必须做假设（这个方案能扩展到100万用户吗）

### Phase 2: 设计实验

#### 2.1 实验原则
- 实验必须能回答问题
- 实验结果必须是可观察的
- 实验必须可重复

#### 2.2 实验设计模板
```
问题：不确定X

假设：X behaves like Y

实验：
1. 准备环境：...
2. 执行操作：...
3. 观察结果：...

预期：如果假设正确 → 观察到...
      如果假设错误 → 观察到...

验证方式：[具体的验证命令/代码]
```

#### 2.3 最小化实验
- 用最小代价验证假设
- 不要为了实验搭一整套环境
- 用单元测试、REPL、简单脚本

### Phase 3: 执行实验

#### 3.1 执行
- 按照设计的步骤执行
- 记录实际观察到的结果
- 不要跳过任何步骤

#### 3.2 分析
- 实际结果和预期一致吗？
- 如果不一致，意味着什么？
- 实验是否引入了新的假设？

#### 3.3 交叉验证
- 用第二个实验验证同一假设
- 用反向实验排除其他可能
- 结合代码阅读验证

### Phase 4: 做出决定

#### 4.1 基于证据决策
- 实验结果是否充分？
- 还有其他不确定性吗？
- 决策的信心水平？

#### 4.2 记录决定和理由
- 做了什么决定？
- 基于什么证据？
- 还有什么不确定性？

## Common Rationalizations

| 常见借口 | 真相 | 反制 |
|---------|------|------|
| "直觉告诉我应该选A" | 直觉往往基于有限经验 | 实验验证假设 |
| "A是主流选择，应该没问题" | 主流不等于适合 | 基于具体场景验证 |
| "StackOverflow这么说，应该对" | StackOverflow答案可能有上下文 | 阅读源码验证 |
| "先选一个，不对再改" | 修改的成本往往比验证高 | 先实验后决定 |

## Red Flags

- 在多个方案之间犹豫超过1天
- 文档和代码行为不一致但不验证
- 说"应该是"但没有验证
- 选择了方案但不确定为什么选
- 遇到bug但不验证根因就修复
- 交接时双方理解不一致但不澄清
