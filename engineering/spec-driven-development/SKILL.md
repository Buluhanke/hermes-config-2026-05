# Spec Driven Development

## Overview

规格文档是开发的合同，不是事后的注释。先写规格让所有人对齐：开发者、测试、评审、产品。规格没写清楚就写代码，是返工的头号原因。

## When to Use

- 开始任何新功能开发
- 实现一个模块的内部逻辑
- 编写重要的算法
- 实现与外部系统的集成
- 任何需要明确"做什么"和"做到什么程度"的时候

## Process

### Phase 1: 理解上下文

#### 1.1 为什么需要这个功能
- 解决了什么问题？
- 谁会使用？
- 使用频率如何？
- 不做会怎样？

#### 1.2 输入和输出
- 输入是什么？（参数、数据格式、来源）
- 输出是什么？（返回值、副作用、格式）
- 边界条件是什么？

#### 1.3 依赖关系
- 依赖哪些模块？
- 被哪些模块依赖？
- 有没有外部依赖？

### Phase 2: 编写规格

#### 2.1 规格格式
```markdown
## 函数/模块名：calculate_discount

### 功能描述
根据用户等级和订单金额计算折扣

### 输入
- user_tier: string ("basic" | "silver" | "gold")
- order_amount: decimal (>= 0)

### 输出
- discount: decimal (0 <= discount <= order_amount)

### 业务规则
1. basic用户：无折扣
2. silver用户：订单>100元部分打9折
3. gold用户：订单>50元部分打8折
4. order_amount为0或负数：抛出ValueError

### 边界条件
- order_amount = 0 → discount = 0
- order_amount = 负数 → ValueError("订单金额必须为正数")
- user_tier不合法 → ValueError("不支持的用户等级")

### 错误处理
- ValueError：输入参数不合法
- 无网络依赖（纯计算函数）

### 性能要求
- 执行时间 < 1ms
- 内存占用 < 1KB
```

#### 2.2 规格检查点
- [ ] 每个输入参数有类型和约束
- [ ] 每个输出有类型和约束
- [ ] 所有边界条件已识别
- [ ] 错误情况已定义
- [ ] 业务规则已明确

#### 2.3 评审规格
- 和调用方确认输入输出理解一致
- 和测试方确认覆盖范围
- 和评审者确认没有歧义

### Phase 3: 基于规格实现

#### 3.1 TDD开发
- 先写测试用例（对应规格的每个场景）
- 再实现最小代码让测试通过
- 重构优化

#### 3.2 规格即文档
- 规格中的每个点都要有对应代码
- 如果代码和规格不一致，更新规格（或修改代码）
- 不要让规格过时

#### 3.3 覆盖度检查
- 规格中的每个分支是否都有测试？
- 边界条件是否覆盖？
- 错误情况是否覆盖？

### Phase 4: 验证与确认

#### 4.1 规格对比
- 逐条对比规格和实现
- 实现是否偏离规格？
- 规格是否有遗漏？

#### 4.2 示例验证
- 用规格中的示例运行代码
- 确认输出和规格一致

## Common Rationalizations

| 常见借口 | 真相 | 反制 |
|---------|------|------|
| "规格太形式化，实际价值不大" | 规格不清是bug和返工的首要原因 | 记录因规格不清导致的返工时间 |
| "代码即文档，注释就够了" | 注释无法描述完整接口契约 | 独立规格文档 |
| "等开发完再补规格" | 开发完往往没有动力补规格 | 规格先行是纪律 |
| "规格写太详细浪费时间" | 规格是最划算的投资 | 简洁但完整，1-2页足够 |

## Red Flags

- 规格和实现明显不一致
- 规格中有模糊的描述（"大致"、"可能"）
- 测试用例和规格不匹配
- 评审时发现各方理解不同
- 边界条件在规格中没有覆盖
- 实现后人发现规格错了

## Verification

验证清单：

- [ ] 规格已书面化
- [ ] 输入输出类型明确
- [ ] 边界条件全覆盖
- [ ] 错误情况已定义
- [ ] 规格已和调用方对齐
- [ ] 测试用例对应规格的每个场景
- [ ] 实现和规格一致
