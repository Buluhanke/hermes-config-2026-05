# Documentation and ADRs

## Overview

代码会变，但决策的上下文会丢失。好的文档和ADR（Architecture Decision Records）让未来的自己和同事知道为什么这样设计，避免重蹈覆辙或盲目重构。

## When to Use

- 完成重要的技术决策
- 选择技术方案时（而不是选其他方案）
- 引入新的依赖
- 架构变更
- 任何需要"记录为什么"的时候

## Process

### Phase 1: 识别需要记录的决策

#### 1.1 什么需要记录
- 任何影响系统架构的决定
- 任何选择A而非B的决定
- 任何引入新工具/框架的决定
- 任何有长期影响的建设

#### 1.2 什么不需要记录
- 纯执行性的决定（今天用哪个变量名）
- 显而易见的决定（有明确最佳实践的）
- 可以从代码直接推断的决定

### Phase 2: 编写ADR

#### 2.1 ADR格式
```markdown
# ADR-001: 使用PostgreSQL而非MySQL

## 状态
已接受

## 日期
2024-01-15

## 背景
需要为新服务选择主数据库。当前团队熟悉MySQL，但某些特性需要JSON支持和全文搜索。

## 决策
使用PostgreSQL作为主数据库。

## 理由
1. JSONB支持：原生JSON操作，无需额外schema设计
2. 全文搜索：内置tsvector/tsquery，不需要ElasticSearch
3. 团队学习：虽然团队更熟悉MySQL，但PostgreSQL学习曲线不高
4. 社区支持：PG在JSON和搜索领域社区更活跃

## 备选方案
1. MySQL + JSON column + 外部搜索
   - 缺点：需要维护两个系统，增加复杂度
2. MongoDB
   - 缺点：事务支持弱，团队不熟悉
3. PostgreSQL（选中）

## 后果
### 正面
- 减少了系统组件数量
- JSON操作在数据库层完成，更高效

### 负面
- 团队需要熟悉PostgreSQL特性
- 部分MySQL经验不能直接复用

### 中性
- 需要迁移现有的MySQL数据
```

#### 2.2 ADR编号
- 使用连续编号（ADR-001, ADR-002...）
- 编号在整个项目生命周期内唯一
- 状态变化不改变编号

### Phase 3: 维护文档

#### 3.1 文档存放位置
```
docs/
├── adr/
│   ├── ADR-001-postgresql-choice.md
│   ├── ADR-002-caching-strategy.md
│   └── README.md（ADR索引）
├── architecture/
│   └── system-overview.md
└── guides/
    └── deployment.md
```

#### 3.2 文档更新
- 当决策变更时，更新ADR状态
- 不要删除旧的ADR，保留历史
- 新决策创建新ADR，不要修改旧ADR

### Phase 4: 文档质量

#### 4.1 好的文档标准
- 读者能独立理解上下文
- 有具体的例子或代码片段
- 区分了事实和意见
- 说明了决策的后果

#### 4.2 常见文档问题
- 只有结论没有理由
- 只有方案没有背景
- 假设读者已经知道上下文
- 文档和代码不一致

## Common Rationalizations

| 常见借口 | 真相 | 反制 |
|---------|------|------|
| "代码即文档，看代码就知道" | 代码不能表达为什么做这个决定 | 记录决策的历史和理由 |
| "决策太显而易见，不需要记录" | 未来的你会忘记当时的考虑 | 记录决策时的可选方案和取舍 |
| "文档写完就过时了" | 过时的文档比没有文档更危险 | 文档是活的，需要维护 |
| "写文档耽误开发时间" | 文档节省的时间远大于写的时间 | 记录维护文档和不需要文档的时间对比 |

## Red Flags

- 决策没有记录
- ADR状态和实际不符
- 文档和代码不一致
- 有多个ADR编号相同
- 文档中只有结论没有理由
- 备选方案没有记录
- 决策后果没有描述

## Verification

验证清单：

- [ ] 重要的技术决策都有ADR
- [ ] ADR格式完整（状态/日期/背景/决策/理由/备选/后果）
- [ ] ADR索引是最新的
- [ ] 备选方案有具体分析
- [ ] 决策后果有正面/负面/中性分类
- [ ] 文档和代码一致
- [ ] 相关人员知道这些文档存在
