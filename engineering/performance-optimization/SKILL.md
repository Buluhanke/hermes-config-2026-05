# Performance Optimization

## Overview

性能优化的第一原则：**先测量，后优化**。不测量就优化是最大的性能浪费来源。优化错误的目标比不优化更糟糕。

## When to Use

- 任何性能问题（响应慢、卡顿、占用高）
- 新功能开发时考虑性能
- 系统容量规划前
- 监控发现性能指标异常
- 重大架构变更前

## Process

### Phase 1: 性能测量

#### 1.1 定义性能目标
- 响应时间目标（P50/P95/P99）
- 吞吐量目标（QPS/TPS）
- 资源利用率目标（CPU/内存/磁盘/网络）
- 业务相关目标（并发用户数、数据处理量）

#### 1.2 建立基准
- 在优化前记录当前性能
- 这是比较的基准线
- 多次测量取稳定值

#### 1.3 性能剖析
- 使用profiler定位热点
- 使用trace工具看调用链
- 使用监控看资源消耗
- 定位具体瓶颈（CPU/IO/网络/锁/GC）

### Phase 2: 分析瓶颈

#### 2.1 常见瓶颈类型
- **CPU密集型**：计算量大，算法复杂度高
- **IO密集型**：磁盘读写、网络等待
- **内存型**：内存分配、GC压力、内存泄漏
- **并发型**：锁竞争、线程阻塞、死锁
- **数据库型**：慢查询、缺失索引、连接池耗尽

#### 2.2 数据库优化
- 慢查询日志分析
- EXPLAIN执行计划
- 索引使用情况
- 连接池配置

#### 2.3 应用层优化
- 算法复杂度（O(n³) → O(n log n)）
- 数据结构选择
- 缓存策略
- 并发模型

### Phase 3: 优化实施

#### 3.1 低垂果实优先
- 缓存重复计算结果
- 懒加载非必需资源
- 批量操作替代循环
- 索引优化

#### 3.2 算法优化
- 减少不必要的计算
- 使用更高效的数据结构
- 空间换时间 or 时间换空间

#### 3.3 缓存策略
- 多级缓存：本地缓存→分布式缓存→数据库
- 缓存失效策略
- 缓存一致性

### Phase 4: 验证优化

#### 4.1 重新测量
- 使用相同的测量方法
- 在相同的环境下测试
- 对比优化前后的数据

#### 4.2 回归测试
- 确认功能没有退化
- 确认没有引入新的问题
- 长时间运行稳定性

#### 4.3 容量规划
- 新性能上限是多少？
- 还能支持多少增长？
- 什么时候需要再次优化？

## Common Rationalizations

| 常见借口 | 真相 | 反制 |
|---------|------|------|
| "直觉告诉我这里需要优化" | 直觉经常是错的 | 必须有数据支撑 |
| "加了缓存就快了" | 错误的缓存策略可能让问题更糟 | 先测量，再决定是否缓存 |
| "升级硬件就能解决" | 硬件升级成本高，且有上限 | 软件优化优先 |
| "上线后再优化" | 上线后优化风险更高 | 性能测试是发布前必须项 |
| "这个算法教科书上说是最优的" | 理论最优不等于实际最优 | 实测验证 |

## Red Flags

- 没有测量数据就声称性能问题
- 优化后没有对比数据
- 优化引入了功能bug
- 只优化了一处但整体没有提升
- 缓存导致数据不一致
- 优化后内存占用增加
- 并发性能反而下降

## Verification

验证清单：

- [ ] 优化前有基准数据
- [ ] 瓶颈已明确定位
- [ ] 优化方案针对根因
- [ ] 优化后性能提升显著（>20%）
- [ ] P95/P99延迟改善
- [ ] 无功能退化
- [ ] 无新的性能问题引入
- [ ] 容量规划已更新
