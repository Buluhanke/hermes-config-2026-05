# Performance Optimization

## Overview

性能优化的第一原则：**先测量，后优化**。不测量就优化是最大的性能浪费来源。优化错误的目标比不优化更糟糕。

## When to Use

- 任何性能问题（响应慢、卡顿、占用高）
- 新功能开发时考虑性能
- 系统容量规划前
- 监控发现性能指标异常
- 重大架构变更前

## Process

### Phase 1: 性能测量

#### 1.1 定义性能目标
- 响应时间目标（P50/P95/P99）
- 吞吐量目标（QPS/TPS）
- 资源利用率目标（CPU/内存/磁盘/网络）
- 业务相关目标（并发用户数、数据处理量）

#### 1.2 建立基准
- 在优化前记录当前性能
- 这是比较的基准线
- 多次测量取稳定值

#### 1.3 性能剖析
- 使用profiler定位热点
- 使用trace工具看调用链
- 使用监控看资源消耗
- 定位具体瓶颈（CPU/IO/网络/锁/GC）

### Phase 2: 分析瓶颈

#### 2.1 常见瓶颈类型
- **CPU密集型**：计算量大，算法复杂度高
- **IO密集型**：磁盘读写、网络等待
- **内存型**：内存分配、GC压力、内存泄漏
- **并发型**：锁竞争、线程阻塞、死锁
- **数据库型**：慢查询、缺失索引、连接池耗尽

#### 2.2 数据库优化
- 慢查询日志分析
- EXPLAIN执行计划
- 索引使用情况
- 连接池配置

#### 2.3 应用层优化
- 算法复杂度（O(n³) → O(n log n)）
- 数据结构选择
- 缓存策略
- 并发模型

### Phase 3: 优化实施

#### 3.1 低垂果实优先
- 缓存重复计算结果
- 懒加载非必需资源
- 批量操作替代循环
- 索引优化

#### 3.2 算法优化
- 减少不必要的计算
- 使用更高效的数据结构
- 空间换时间 or 时间换空间

#### 3.3 缓存策略
- 多级缓存：本地缓存→分布式缓存→数据库
- 缓存失效策略
- 缓存一致性

#### 3.4 Token预算控制

Token是LLM调用的主要成本和吞吐量瓶颈。合理的Token管理可以大幅降低成本并提升响应速度。

**输入侧优化：**
- **上下文压缩**：长对话历史进行摘要压缩，去除冗余信息
- ** Selective Context**：只保留与当前任务相关的上下文片段
- **消息窗口管理**：定期触发摘要，保留关键信息
- **系统提示词精简**：移除冗余的指令和示例

**输出侧优化：**
- **结构化输出**：明确指定输出格式，避免无效Token
- **长度约束**：通过prompt限制响应长度
- **流式输出**：对于长回复使用流式，减少等待时间

**Token监控：**
```
单次请求Token = prompt_tokens + completion_tokens
总成本 ≈ (prompt_tokens × 单价 + completion_tokens × 单价) × 请求量
```

**预算分配策略：**
- 为不同任务类型设置Token上限
- 高频任务优先压缩，高成本任务优先优化逻辑
- 监控Token消耗趋势，提前预警

#### 3.5 工具调用优化

频繁的工具调用是AI Agent的主要性能瓶颈。优化工具调用可以显著提升整体效率。

**调用频率控制：**
- **Batching**：将多个同类操作合并为一次调用
- **节流（Throttling）**：限制高频操作（如搜索、查询）的调用频率
- **去重**：相同参数的重复调用直接返回缓存结果

**调用链优化：**
- **并行化**：独立的工具调用并行执行（见3.6）
- **短路策略**：根据中间结果提前终止不必要的调用链
- **Fallback层**：工具失败时使用轻量级替代方案

**工具选择策略：**
```
任务复杂度低 → 使用轻量工具（计算器、查表）
任务复杂度中 → 使用单一功能工具（搜索、API调用）
任务复杂度高 → 分解为多次工具调用，但控制深度
```

**工具性能基准：**
- 快速工具（<50ms）：计算器、正则、格式转换
- 中速工具（50-500ms）：文件IO、网络API、数据库查询
- 慢速工具（>500ms）：大模型推理、复杂搜索、批量处理

#### 3.6 并发vs串行选择

并发和串行的选择直接影响系统吞吐量和响应延迟。错误的选择可能导致性能下降甚至资源耗尽。

**何时选择串行：**
- 任务存在依赖关系（后一步需要前一步的结果）
- 存在共享资源的竞争（如数据库连接、文件锁）
- 任务之间有状态传递
- 资源受限（内存、带宽）

**何时选择并发：**
- 多个独立任务可以同时执行
- I/O密集型操作（等待时间长，适合等待时做其他事）
- 需要降低整体响应时间（并行执行取max而非sum）
- 任务可以分片处理

**并发模式选择：**
```
┌─────────────────────────────────────────────────────────┐
│  并发模型           适用场景            注意事项          │
├─────────────────────────────────────────────────────────┤
│  ThreadPool        CPU密集型          控制线程数         │
│  AsyncIO          I/O密集型          避免阻塞           │
│  ProcessPool      CPU+隔离需求        开销较大           │
│  Rate Limiter     API调用限流         合理设置QPS        │
│  Semaphore        资源并发限制         避免死锁           │
└─────────────────────────────────────────────────────────┘
```

**并发度决策公式：**
```
最优并发数 ≈ 线程数 = CPU核心数 / (1 - 阻塞系数)
阻塞系数 = I/O等待时间 / 总时间
```

**串行转并行的常见场景：**
- 多个独立的API调用 → asyncio.gather 或 ThreadPoolExecutor
- 批量数据处理 → 分割后并行处理再合并
- 多数据源的聚合查询 → 并行查询再汇总

#### 3.7 内存泄漏检测

内存泄漏会导致系统性能逐渐下降，最终导致OOM崩溃。对于长期运行的AI Agent尤为重要。

**常见泄漏模式：**
- **缓存无限增长**：缓存没有淘汰策略
- **事件监听器未移除**：反复添加但从不移除
- **闭包持有引用**：长时间存在的对象持有临时对象引用
- **全局状态累积**：历史记录、对话上下文无限增长
- **第三方库泄漏**：某些库存在已知泄漏

**检测方法：**
```python
# Python: tracemalloc 检测内存增长
import tracemalloc
tracemalloc.start()

# ... 执行可疑代码 ...

snapshot = tracemalloc.take_snapshot()
top_stats = snapshot.statistics('lineno')
for stat in top_stats[:10]:
    print(stat)
```

```javascript
// JavaScript: 内存快照对比
// DevTools → Memory → Heap Snapshot → Compare Snapshots
```

**监控指标：**
```
内存增长率 = (当前内存 - 基线内存) / 运行时间
如果增长率 > 0 且不收敛，说明存在泄漏
```

**自动检测工具：**
- Python: `tracemalloc`, `objgraph`, `memory_profiler`
- JavaScript: `node --inspect`, Chrome DevTools`, `Clinic.js`
- 系统级: `valgrind`, `AddressSanitizer`

**预防措施：**
- 设置内存上限和自动重启机制
- 对缓存大小设置硬限制（LRU淘汰）
- 定期触发GC或手动释放大对象
- 记录内存使用趋势，设置告警

### Phase 4: 验证优化

#### 4.1 重新测量
- 使用相同的测量方法
- 在相同的环境下测试
- 对比优化前后的数据

#### 4.2 回归测试
- 确认功能没有退化
- 确认没有引入新的问题
- 长时间运行稳定性

#### 4.3 容量规划
- 新性能上限是多少？
- 还能支持多少增长？
- 什么时候需要再次优化？

## Common Rationalizations

| 常见借口 | 真相 | 反制 |
|---------|------|------|
| "直觉告诉我这里需要优化" | 直觉经常是错的 | 必须有数据支撑 |
| "加了缓存就快了" | 错误的缓存策略可能让问题更糟 | 先测量，再决定是否缓存 |
| "升级硬件就能解决" | 硬件升级成本高，且有上限 | 软件优化优先 |
| "上线后再优化" | 上线后优化风险更高 | 性能测试是发布前必须项 |
| "这个算法教科书上说是最优的" | 理论最优不等于实际最优 | 实测验证 |

## Red Flags

- 没有测量数据就声称性能问题
- 优化后没有对比数据
- 优化引入了功能bug
- 只优化了一处但整体没有提升
- 缓存导致数据不一致
- 优化后内存占用增加
- 并发性能反而下降

## Verification

验证清单：

- [ ] 优化前有基准数据
- [ ] 瓶颈已明确定位
- [ ] 优化方案针对根因
- [ ] 优化后性能提升显著（>20%）
- [ ] P95/P99延迟改善
- [ ] 无功能退化
- [ ] 无新的性能问题引入
- [ ] 容量规划已更新
