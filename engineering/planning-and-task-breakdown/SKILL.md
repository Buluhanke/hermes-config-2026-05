# Planning and Task Breakdown

## Overview

把模糊的目标变成明确的执行步骤。规划不是"想清楚再做"，而是"边做边想清楚"——规划本身也是工作步骤，需要分解和执行。

## When to Use

- 任何模糊的、不知道从哪里开始的任务
- 任何预计超过几小时的工件
- 任何涉及多人协作的项目
- 任何技术方案需要选型的任务
- Sprint planning、需求评审、技术设计时

## Process

### Phase 1: 理解目标

#### 1.1 明确最终产出
- 用一句话描述交付物
- 什么人会用这个产出？
- 解决了什么问题？
- 如何验证交付成功？

#### 1.2 理解约束
- 时间限制（deadline是什么？）
- 技术限制（只能用XX技术栈？）
- 资源限制（只有一个人？只有XX预算？）
- 质量底线（什么标准必须达到？）

#### 1.3 识别风险
- 最坏情况是什么？
- 哪些地方最容易出问题？
- 哪些是未知领域（需要探索）？

### Phase 2: 粗粒度分解

#### 2.1 定义阶段（Phase）
- 完整交付物分成几个大阶段？
- 每个阶段的产出是什么？
- 阶段之间的依赖是什么？

#### 2.2 估算每个阶段
- 每个阶段预计多少时间？
- 是否有外部依赖？
- 可以并行吗？

#### 2.3 定义里程碑
- 什么时间点必须交付什么？
- 哪些是硬截止（hard deadline）？
- 哪些是软截止（soft deadline）？

### Phase 3: 细粒度分解

#### 3.1 分解到2小时粒度
- 每个子任务≤2小时
- 每个子任务有明确的完成标准
- 每个子任务可以独立验证

#### 3.2 识别任务依赖
- 哪些任务必须先完成？
- 哪些可以并行？
- 哪些有外部依赖？

#### 3.3 定义验收条件
- 子任务完成的标准是什么？
- 如何测试/验证？
- 谁来验收？

### Phase 4: 执行规划

#### 4.1 排序
- 按依赖关系排序
- 按风险高低排序（风险高的先做）
- 按价值排序（高价值的先做）

#### 4.2 分配资源
- 谁来做每个任务？
- 需要什么工具/环境？
- 需要什么外部支持？

#### 4.3 建立检查点
- 每日站会检查什么？
- 什么情况下需要调整计划？
- 什么时候说"不"？

### Phase 5: 追踪与调整

#### 5.1 每日检查
- 今天完成了什么？
- 明天要做什么？
- 有没有阻塞项？

#### 5.2 调整计划
- 实际vs计划差距有多大？
- 需要调整范围/时间/质量？
- 要不要通知相关方？

#### 5.3 复盘
- 预估和实际的差距
- 哪些做得好？
- 哪些需要改进？

## Common Rationalizations

| 常见借口 | 真相 | 反制 |
|---------|------|------|
| "需求还不清楚，等清楚了再规划" | 规划本身就是理清需求的方式 | 先做粗粒度规划，在执行中细化 |
| "这个任务简单，不需要规划" | 简单任务不需要规划，复杂任务才需要 | 如果无法在5分钟内说清楚步骤，就需要规划 |
| "规划浪费时间，直接干更快" | 无规划的干法会在错误方向走更远 | 记录无规划时浪费的时间，对比规划节省的时间 |
| "我不能做决定，等别人来定" | 规划者需要做出决策，并承担决策风险 | 至少提出几个选项，并推荐一个 |
| "变化太多，规划赶不上变化" | 规划不是为了预测未来，是为了应对变化 | 规划本身就是管理变化的方式 |
| **"我先问你确认一下再做"** | **老板倾向自主判断后直接执行** | **对于有明确解决方向的任务，直接执行；只问需要决策的选择题** |

## Red Flags

- 无法用一句话描述最终交付物
- 任务分解后有超过7个步骤
- 有任务无法定义验收条件
- 有任务的完成标准是"完成了就行"
- 有人对任务理解不一致（没有对齐）
- 分解到最细还是觉得"这件事很复杂"
- 估算时间加起来远超可用时间

## Verification

验证清单：

- [ ] 最终交付物已明确描述
- [ ] 已识别所有外部依赖和约束
- [ ] 已分成≤2小时的细粒度任务
- [ ] 每个任务有明确的验收条件
- [ ] 任务之间依赖关系已标注
- [ ] 有明确的里程碑和截止时间
- [ ] 风险已识别并有应对方案
- [ ] 计划已和所有相关方对齐
