# Planning and Task Breakdown

## Overview

把模糊的目标变成明确的执行步骤。规划不是"想清楚再做"，而是"边做边想清楚"——规划本身也是工作步骤，需要分解和执行。

## When to Use

- 任何模糊的、不知道从哪里开始的任务
- 任何预计超过几小时的工件
- 任何涉及多人协作的项目
- 任何技术方案需要选型的任务
- Sprint planning、需求评审、技术设计时

## Process

### Phase 1: 理解目标

#### 1.1 明确最终产出
- 用一句话描述交付物
- 什么人会用这个产出？
- 解决了什么问题？
- 如何验证交付成功？

#### 1.2 理解约束
- 时间限制（deadline是什么？）
- 技术限制（只能用XX技术栈？）
- 资源限制（只有一个人？只有XX预算？）
- 质量底线（什么标准必须达到？）

#### 1.3 识别风险
- 最坏情况是什么？
- 哪些地方最容易出问题？
- 哪些是未知领域（需要探索）？

### Phase 2: 粗粒度分解

#### 2.1 定义阶段（Phase）
- 完整交付物分成几个大阶段？
- 每个阶段的产出是什么？
- 阶段之间的依赖是什么？

#### 2.2 估算每个阶段
- 每个阶段预计多少时间？
- 是否有外部依赖？
- 可以并行吗？

#### 2.3 定义里程碑
- 什么时间点必须交付什么？
- 哪些是硬截止（hard deadline）？
- 哪些是软截止（soft deadline）？

### Phase 3: 细粒度分解

#### 3.1 分解到2小时粒度
- 每个子任务≤2小时
- 每个子任务有明确的完成标准
- 每个子任务可以独立验证

#### 3.2 识别任务依赖
- 哪些任务必须先完成？
- 哪些可以并行？
- 哪些有外部依赖？

#### 3.3 定义验收条件
- 子任务完成的标准是什么？
- 如何测试/验证？
- 谁来验收？

### Phase 4: 执行规划

#### 4.1 排序
- 按依赖关系排序
- 按风险高低排序（风险高的先做）
- 按价值排序（高价值的先做）

#### 4.2 分配资源
- 谁来做每个任务？
- 需要什么工具/环境？
- 需要什么外部支持？

#### 4.3 建立检查点
- 每日站会检查什么？
- 什么情况下需要调整计划？
- 什么时候说"不"？

### Phase 5: 追踪与调整

#### 5.1 每日检查
- 今天完成了什么？
- 明天要做什么？
- 有没有阻塞项？

#### 5.2 调整计划
- 实际vs计划差距有多大？
- 需要调整范围/时间/质量？
- 要不要通知相关方？

#### 5.3 复盘
- 预估和实际的差距
- 哪些做得好？
- 哪些需要改进？

## Common Rationalizations

| 常见借口 | 真相 | 反制 |
|---------|------|------|
| "需求还不清楚，等清楚了再规划" | 规划本身就是理清需求的方式 | 先做粗粒度规划，在执行中细化 |
| "这个任务简单，不需要规划" | 简单任务不需要规划，复杂任务才需要 | 如果无法在5分钟内说清楚步骤，就需要规划 |
| "规划浪费时间，直接干更快" | 无规划的干法会在错误方向走更远 | 记录无规划时浪费的时间，对比规划节省的时间 |
| "我不能做决定，等别人来定" | 规划者需要做出决策，并承担决策风险 | 至少提出几个选项，并推荐一个 |
| "变化太多，规划赶不上变化" | 规划不是为了预测未来，是为了应对变化 | 规划本身就是管理变化的方式 |
| **"我先问你确认一下再做"** | **老板倾向自主判断后直接执行** | **对于有明确解决方向的任务，直接执行；只问需要决策的选择题** |

## Red Flags

- 无法用一句话描述最终交付物
- 任务分解后有超过7个步骤
- 有任务无法定义验收条件
- 有任务的完成标准是"完成了就行"
- 有人对任务理解不一致（没有对齐）
- 分解到最细还是觉得"这件事很复杂"
- 估算时间加起来远超可用时间

## Phase 6: 多线程任务协调

当多个任务流需要同时推进时，协调成为关键能力。

### 6.1 任务分类

| 类型 | 特征 | 协调方式 |
|------|------|---------|
| 独立任务 | 无依赖，可并行 | 直接分配资源 |
| 顺序依赖 | A→B→C | 串行，关键路径优先 |
| 条件分支 | A完成决定B/C | 监控A结果，动态分配 |
| 环形依赖 | A→B→C→A | 重构，消除环 |

### 6.2 并行度决策

**Amdahl定律**：加速比 = 1 / (S + P/N)
- S = 串行部分比例
- P = 可并行部分比例
- N = 并行worker数

**实用准则**：
- 并行前先确认任务有足够独立子任务
- 增加并行度有开销（通信、同步），超过临界点反而降效
- IO密集型任务并行收益高，CPU密集型需谨慎

### 6.3 资源分配矩阵

```
              | 人员A | 人员B | 人员C
-------------|-------|-------|------
任务流1      |   ●   |       |
任务流2      |       |   ●   |   ●
任务流3      |       |       |   ●
```

- ● = 主要负责人，○ = 备份/协作
- 避免单点故障：每个关键任务流至少有1名备份
- 上下文切换成本：同一人员切换任务流需预留20%缓冲时间

### 6.4 协调机制

**日常协调**：
- 每日站会：每人3分钟（昨天/今天/阻塞）
- 任务墙：可视化所有任务流状态
- 阻塞升级：2小时无法解决的阻塞立即升级

**跨团队协调**：
- 接口边界文档化，减少等待
- 约定交付时间节点（含缓冲）
- 指定单一对接人，避免多头沟通

### 6.5 常见问题处理

| 问题 | 原因 | 解决方案 |
|------|------|---------|
| 任务流卡住 | 依赖外部输入 | 提前识别，列出等待清单 |
| 资源争抢 | 并行度过高 | 降低并行度或增加资源 |
| 质量下降 | 上下文切换过多 | 任务批处理，减少切换 |
| 人员倦怠 | 单人任务流过长 | 强制轮换，保持新鲜度 |

## Phase 7: 依赖管理与拓扑排序

### 7.1 依赖类型

```
类型           | 符号  | 示例                        | 管理策略
--------------|-------|-----------------------------|------------------
Finish→Start  | FS    | A完成，B才能开始            | 硬性阻塞
Start→Start   | SS    | A和B同时开始                 | 同步启动
Finish→Finish | FF    | A和B同时结束                 | 同步收尾
Start→Finish  | SF    | A开始后，B必须结束（罕见）   | 极少用，需重构
```

### 7.2 拓扑排序算法

**Kahn算法**（BFS风格）：
```
1. 计算所有节点的入度
2. 将入度=0的节点加入队列（可立即执行）
3. 取出队首，执行之，删除其出边，更新相邻节点入度
4. 将新入度=0的节点加入队列
5. 重复3-4直到队列为空
```

**Python实现**：
```python
from collections import deque

def topological_sort(tasks: dict[str, list[str]]) -> list[str]:
    """
    tasks: {task_name: [dependencies]}
    returns: 拓扑排序后的任务列表
    """
    # 计算入度
    in_degree = {node: 0 for node in tasks}
    for deps in tasks.values():
        for dep in deps:
            in_degree[dep] = in_degree.get(dep, 0) + 1
    
    # 入度为0的节点可立即执行
    queue = deque([node for node, deg in in_degree.items() if deg == 0])
    result = []
    
    while queue:
        node = queue.popleft()
        result.append(node)
        # 模拟删除该节点的影响
        for next_node in tasks.get(node, []):
            in_degree[next_node] -= 1
            if in_degree[next_node] == 0:
                queue.append(next_node)
    
    # 检测环
    if len(result) != len(tasks):
        cycle = set(tasks.keys()) - set(result)
        raise ValueError(f"环形依赖 detected: {cycle}")
    
    return result
```

### 7.3 关键路径识别

**关键路径**：决定项目最短完成时间的最长路径

```
识别方法：
1. 做拓扑排序
2. 计算每个节点的最早开始时间(EST)和最晚开始时间(LST)
3. EST = LST 的节点在关键路径上
```

**计算公式**：
- EST(最早开始) = max(所有前置任务的EST + 工期)
- LST(最晚开始) = min(所有后续任务的LST - 本任务工期)
- 浮动时间 = LST - EST

用ASCII图表示任务依赖：

              ↓               │

[前端开发] [后端开发] [DB设计]  │

### 7.5 依赖管理最佳实践

1. **显式声明**：所有依赖必须在代码/文档中显式声明
2. **接口先行**：依赖方和被依赖方先约定接口，再各自开发
3. **Mock隔离**：外部依赖用mock替代，避免阻塞
4. **增量验证**：每完成一个节点就验证，减少最后发现问题的风险
5. **依赖审查**：新增依赖必须经过评审，警惕依赖蔓延

## Phase 8: 风险识别与规避

### 8.1 风险分类

| 类别 | 典型风险 | 发生概率 | 影响程度 |
|------|---------|---------|---------|
| 技术风险 | 技术方案不可行、第三方服务宕机 | 中 | 高 |
| 人员风险 | 关键人员离职、团队能力不足 | 低 | 极高 |
| 外部风险 | 政策变化、供应商违约、市场变化 | 中 | 高 |
| 范围风险 | 需求蔓延、验收标准不清 | 高 | 中 |
| 进度风险 | 估算偏差、阻塞未及时升级 | 高 | 中 |

### 8.2 风险识别方法

**系统性识别**：
- **WBS分解法**：每个工作包逐个分析"会出什么问题"
- ** checklist法**：使用历史项目风险清单逐项检查
- **专家访谈**：邀请有经验的人回忆类似项目的失败案例
- **前车之鉴**：复盘以往项目的风险事件

**结构化分析**：
```
风险 = 发生概率 × 影响程度

高风险(>70)：必须立即处理
中风险(30-70)：需要应对计划
低风险(<30)：接受或监控
```

### 8.3 风险应对策略

| 策略 | 适用场景 | 具体做法 |
|------|---------|---------|
| 规避 | 风险高且可选择 | 改变方案绕过，不做这件事 |
| 转移 | 无法规避但可分散 | 买保险、外包、对冲 |
| 缓解 | 概率或影响可降低 | 冗余设计、降低复杂度、增加测试 |
| 接受 | 低风险或无法处理 | 准备应急预算/时间，留出缓冲 |
| 上报 | 超出团队能力范围 | 立即升级，明确决策需求 |

## Phase 10: 敏捷迭代模式

### 10.1 迭代周期选择

| 周期 | 适用场景 | 优点 | 缺点 |
|------|---------|------|------|
| 1周 Sprint | 快速响应、频繁交付 | 反馈快、适应强 | 规划开销大 |
| 2周 Sprint | 主流选择 | 平衡深度与速度 | 等待成本 |
| 3-4周 Sprint | 大型特性、长周期任务 | 减少切换损耗 | 反馈慢 |
| 持续交付 | 独立服务、DevOps成熟 | 无等待、快速价值 | 基础设施要求高 |

### 10.2 Sprint Planning怎么做

**会前准备**（1小时）：
- Product Owner排优先级
- 团队估算工作量
- 确认依赖关系

**会议流程**（1-2小时）：
```
1. 回顾上Sprint（15分钟）
   - 完成什么？
   - 遇到什么？
   - 学到什么？

2. 本Sprint目标（5分钟）
   - 业务目标是什么？
   - 验收标准？

3. 选择Backlog（30分钟）
   - 按优先级逐条讨论
   - 团队决策能完成多少
   - 明确完成标准

4. 任务分解（30分钟）
   - 拆解到1-2天粒度
   - 识别依赖
   - 分配责任人

5. 承诺（5分钟）
   - 团队集体承诺
   - 记录假设和风险
```

### 10.3 迭代速率计算

**历史速率法**：
```
平均速率 = (Sprint1 + Sprint2 + ... + SprintN) / N

下个Sprint可完成故事点 = 平均速率 × 调整因子

调整因子：
- 上个Sprint有人休假 → 0.8
- 有新技术引入 → 0.7
- 团队稳定、流程成熟 → 1.0
```

### 10.4 敏捷常见反模式

| 反模式 | 症状 | 解决方案 |
|--------|------|---------|
| 伪敏捷 | 叫Sprint但无回顾、仪式全无 | 逐步引入，先做有价值的 |
| 数字驱动 | 只关注点数，不关注质量 | 关注价值交付，而非速度 |
| 范围游戏 | PO随意加需求，Sprint无固定 | 严格Sprint范围保护 |
| 孤岛工作 | 没人知道别人在做什么 | 每日站会、结对编程 |
| 英雄主义 | 靠个人熬夜完成 | 团队承诺，集体负责 |

### 10.5 敏捷度量

```
核心指标：

1.  velocity（速率）
   - 上线可用点数/ Sprint
   - 用于预测，不用于考核

2.  循环周期（Lead Time）
   - 需求提出到上线的时间
   - 越短越好

3.  部署频率
   - 生产环境部署次数/周
   - DevOps成熟度指标

4.  变更失败率
   - 部署后回滚/问题比例
   - 反映质量

5.  阻塞时间
   - 任务从blocked到恢复的时间
   - 越长说明协调越差
```

### 10.6 持续改进机制

**Sprint回顾模板**：
```markdown
## Sprint回顾 - Sprint N

### 继续保持 (Continue)
- 每日站会简短高效
- 代码审查及时

### 需要改进 (Improve)
- 测试覆盖率不足
- 阻塞升级不够及时

### 改进承诺 (Action Items)
| 改进项 | 负责人 | 目标 | 验收方式 |
|-------|-------|------|---------|
| 增加单元测试 | @张三 | Sprint结束前 | 覆盖率>70% |
| 阻塞立即升级 | 全体 | 即时 | 站会检查 |

### 整体评分：6/10
（10=完美，6=达标但有改进空间）
```

### 10.7 不同团队的敏捷适配

| 团队类型 | 推荐模式 | 注意事项 |
|---------|---------|---------|
| 初创小团队(<5人) | 轻量Kanban | 少仪式，多专注工作 |
| 中型团队(5-15人) | Scrum | 角色完整，仪式到位 |
| 大型团队(>15人) | Scrum of Scrums | 分小队，跨团队协调 |
| 远程团队 | 异步优先 | 文档详尽，时区协调 |
| 维护型团队 | Kanban | 持续流，进度可视化 |
