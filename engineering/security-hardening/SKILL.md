# Security Hardening

## Overview

安全不是事后检查，是从设计阶段开始的系统工程。OWASP Top 10覆盖了绝大多数常见漏洞，但每个系统有自己独特的攻击面。

## When to Use

- 任何涉及用户认证的功能
- 任何涉及权限控制的功能
- 任何涉及敏感数据的存储或传输
- 任何涉及外部输入的功能
- 上线前的安全检查
- 发现安全漏洞后的修复

## Process

### Phase 1: 威胁建模

#### 1.1 识别资产
- 什么是需要保护的？（用户数据、支付信息、API密钥、业务逻辑）
- 什么被公开暴露？（API、用户界面、管理后台）

#### 1.2 识别攻击面
- 数据入口点？（用户输入、文件上传、第三方API）
- 数据存储点？（数据库、文件系统、缓存）
- 认证机制？（用户名密码、OAuth、API Key、Session）

#### 1.3 识别威胁
- 谁可能攻击？（外部攻击者、恶意用户、内部人员）
- 攻击动机？（数据窃取、权限提升、服务中断）
- 攻击方式？（SQL注入、XSS、CSRF、社会工程）

### Phase 2: OWASP Top 10 检查

#### 2.1 A01: Broken Access Control
- 用户能否访问不该访问的数据？
- 水平越权：用户A能否访问用户B的数据？
- 垂直越权：普通用户能否访问管理员功能？
- IDOR：使用直接对象引用时是否验证权限？

#### 2.2 A02: Cryptographic Failures
- 敏感数据是否加密存储？
- 传输层是否使用TLS？
- 密码是否用强哈希算法（bcrypt/argon2）？
- 密钥是否硬编码在代码中？

#### 2.3 A03: Injection
- 用户输入是否经过验证和清洗？
- SQL查询是否使用参数化查询？
- OS命令是否允许用户输入？
- 文件路径是否验证？

#### 2.4 A04: Insecure Design
- 是否有速率限制（防止暴力破解）？
- 是否有账户锁定机制？
- 是否有完整的日志记录？
- 错误信息是否泄露敏感信息？

#### 2.5 A05: Security Misconfiguration
- 默认凭据是否更改？
- 不必要的服务是否关闭？
- 错误处理是否安全？
- 安全头是否配置？

#### 2.6 A06: Vulnerable Components
- 第三方库是否最新版本？
- 是否有已知漏洞的依赖？
- 组件来源是否可信？
- 是否使用不维护的组件？

#### 2.7 A07: Authentication Failures
- 密码强度要求是否合理？
- 会话ID是否随机且安全生成？
- 会话过期机制是否正确？
- 多因素认证是否可用？

#### 2.8 A08: Software and Data Integrity
- 第三方CDN/库是否验证hash？
- CI/CD流程是否安全？
- 代码来源是否可信？
- 部署包是否验证完整性？

#### 2.9 A09: Security Logging
- 认证事件是否记录？
- 访问控制失败是否记录？
- 日志是否包含敏感信息？
- 日志是否防篡改？

#### 2.10 A10: SSRF
- 用户提供的URL是否验证？
- 是否限制可访问的内网地址？
- 是否有白名单机制？
- 错误信息是否泄露内网信息？

### Phase 3: 安全测试

#### 3.1 自动化扫描
- 使用SAST工具扫描代码
- 使用DAST工具扫描运行应用
- 使用依赖检查工具（OWASP Dependency-Check）

#### 3.2 手动渗透测试
- 关键功能的手动测试
- API接口的越权测试
- 社会工程学测试（钓鱼邮件模拟）

#### 3.3 代码审计
- 敏感函数的代码审查
- 认证授权逻辑的代码审查
- 加密实现的代码审查

### Phase 4: 修复与验证

#### 4.1 修复优先级
- 按风险等级排序
- 高风险立即修复
- 中风险本周修复
- 低风险下个版本修复

#### 4.2 修复验证
- 修复后重新扫描
- 验证漏洞不再存在
- 记录修复方式

## Common Rationalizations

| 常见借口 | 真相 | 反制 |
|---------|------|------|
| "这是内网系统，不需要安全" | 内网也会被攻击，而且攻击后影响更大 | 零信任原则：默认不信任任何网络 |
| "我们太小，没人攻击" | 小公司更容易成为目标，因为攻击成本低 | 记录行业安全事件作为参考 |
| "用了HTTPS就安全了" | HTTPS只加密传输层，应用层漏洞依然存在 | 完整的安全架构检查 |
| "用户密码加密了就行" | 加密不等于哈希，弱加密可被逆向 | 使用bcrypt/argon2等专业密码哈希 |
| "第三方库是开源的，应该安全" | 开源组件有已知漏洞是常态 | 定期更新依赖，使用依赖检查工具 |

## Red Flags

- 任何用户输入不经过验证直接使用
- 任何敏感信息明文存储或传输
- 任何硬编码的密码或密钥
- 任何绕过认证/授权的代码
- 任何SQL拼接用户输入
- 任何文件路径使用用户输入拼接
- 任何错误信息泄露内部结构

## 新增：1688采购支付安全

### 1.1 1688开放平台API安全

#### 认证与授权
- **AppKey + AppSecret**：妥善保管在服务端环境变量或密钥管理服务，绝不暴露在前端或代码仓库
- **AccessToken**：有效期通常2小时，需使用refresh_token续期，token存加密存储而非内存或日志
- **签名算法**：1688采用MD5/HMAC-SHA1签名，签名密钥不得硬编码，需动态获取

#### 请求安全
- 请求频率限制：QPS通常为10，突破限制会封禁IP
- 使用HTTPS全部通信，验证服务器证书
- 请求参数做好防重放：加入timestamp和nonce

#### 订单与支付风控
- 买家支付后回调（TradeRate参数）需验证签名防止伪造
- 大额订单触发人工审核流程，不依赖单一自动化判断
- 批量采购做好幂等设计，防止重复下单

### 1.2 支付宝担保交易安全

- 回调通知（notify_url）需验证：
  - 支付宝返回的sign是否正确
  - out_trade_no是否自家订单号
  - trade_status是否为TRADE_SUCCESS
  - total_amount是否匹配（防止金额篡改）
- 不得将支付宝私钥暴露在任何客户端
- 异步通知需做幂等处理（同一notify_id只处理一次）

### 1.3 资金流水风险

- 日对账机制：每日核对平台侧流水与本地记录是否一致
- 差异排查流程：金额不符、状态不一致的自动告警
- 大额转账双人复核制度
- 退款必须原路退回，不允许现金或私下转账

## 新增：凭证保护（Cookie/Token/API Key）

### 2.1 敏感凭证清单

| 凭证类型 | 风险等级 | 典型场景 |
|---------|---------|---------|
| 数据库密码 | 极高 | 配置文件中 |
| API Key/Secret | 极高 | 1688/微信/支付宝等第三方 |
| JWT/AccessToken | 高 | 用户会话 |
| RefreshToken | 高 | token续期 |
| Cookie/Session | 高 | Web会话 |
| SSH密钥 | 极高 | 服务器访问 |
| TLS证书私钥 | 极高 | HTTPS服务 |

### 2.2 存储规范

#### 禁止做法
- 硬编码在源代码（即使私有仓库）
- 写在配置文件但提交到git
- 打印在日志中（包含调试日志）
- 存在代码注释里
- 放在前端代码或前端存储

#### 推荐做法
- 环境变量注入（docker run -e 或 K8s Secret）
- 专用的密钥管理服务（AWS Secrets Manager / HashiCorp Vault / Azure Key Vault）
- 加密存储：aes-256-gcm加密后存数据库或文件，密钥由主密钥保护
- 密钥轮换：定期自动更换，最长90天

### 2.3 传输安全

- Cookie设置：`Secure` + `HttpOnly` + `SameSite=Strict/Lax`
- Token放在Authorization Header而非URL（URL会被浏览器历史和服务器日志记录）
- 敏感接口强制TLS 1.2+，禁用TLS 1.0/1.1和SSL
- 内部服务间调用也用mTLS双向认证

### 2.4 凭证生命周期管理

```
创建 → 安全存储 → 最小化使用 → 定期轮换 → 失效销毁
```

- 创建：随机生成（cryptographically secure RNG），足够长度（API Key至少32字符）
- 使用：日志中脱敏显示（如 `AK****1234`），错误信息不返回完整key
- 轮换：主动轮换（定期）+ 被动轮换（泄露后立即）
- 失效： token泄露后立刻失效所有相关会话并告警

## 新增：反爬法律边界与风险

### 3.1 法律框架

#### 中国法律
- **《网络安全法》** 第27条：不得非法侵入他人网络、窃取网络数据
- **《数据安全法》**：重要数据的收集、存储有合规要求
- **《个人信息保护法》**：**未经授权抓取个人信息可能构成违法**
- **《刑法》** 第285条：提供侵入/非法控制计算机信息系统程序罪

#### 民事风险
- 不正当竞争：竞争对手抓取数据用于竞争
- 侵权：抓取受版权保护内容
- 违约：违反平台服务协议（ToS）

### 3.2 平台服务协议（ToS）红线

几乎所有主流平台明确禁止：
- 未经授权的自动化访问（爬虫/bot）
- 绕过反爬措施（如验证码、IP封禁）
- 批量数据收集
- 使用收集数据用于商业目的（除非明确授权）

典型ToS处罚：**封号、IP封禁、法律追究**

### 3.3 技术边界（规避刑事责任的最低要求）

| 行为 | 法律风险 | 合规做法 |
|-----|---------|---------|
| 公开页面少量抓取 | 低 | 遵守robots.txt，限速 |
| 登录后抓取自身数据 | 低 | 用户授权，数据自用 |
| 绕过验证码/反爬 | 中高 | 不绕过，使用官方API |
| 抓取个人信息 | 高 | 必须授权，禁止贩卖 |
| 抓取商业机密 | 高 | 绝对禁止 |
| DDoS式抓取 | 高 | 限速，保护对方服务 |

### 3.4 合规爬虫 checklist

- [ ] 遵守robots.txt（法律非强制，但体现善意）
- [ ] 设置合理的请求间隔（≥3秒/次）
- [ ] 使用User-Agent标识自己（善意爬虫）
- [ ] 不绕过验证码/反爬机制
- [ ] 不抓取明确声明保密的数据
- [ ] 不传播抓取的数据
- [ ] 仅抓取授权范围的数据
- [ ] 记录抓取行为日志（自证善意）

### 3.5 如果收到侵权通知

1. **立即停止**：停止相关抓取行为
2. **评估请求**：区分合法通知与恶意敲诈
3. **证据保全**：保存爬取日志、代码、授权记录
4. **法律咨询**：涉及个人信息/商业秘密需专业介入
5. **整改回复**：向平台/权利人说明整改措施

## 新增：日志脱敏

### 4.1 敏感数据定义

必须脱敏的敏感字段：

| 类别 | 典型字段 |
|-----|---------|
| 认证凭证 | password, token, api_key, secret, session_id |
| 个人身份 | id_card, passport, name, phone, email |
| 金融信息 | bank_card, card_number, cvv, account |
| 医疗健康 | medical_record, diagnosis, prescription |
| 地址位置 | home_address, gps坐标 |
| 业务敏感 | 客户报价, 供应商成本, 商业合同金额 |

### 4.2 脱敏规则库

```python
# 通用脱敏规则示例
DESENSITIZE_RULES = {
    # 姓名：张三 → 张*
    "name": lambda v: v[0] + "*" if len(v) > 1 else "*",
    
    # 手机：13812345678 → 138****5678
    "phone": lambda v: v[:3] + "****" + v[-4:] if len(v) >= 11 else "****",
    
    # 身份证：110101199001011234 → 110101********1234
    "id_card": lambda v: v[:6] + "********" + v[-4:] if len(v) >= 10 else "****",
    
    # 银行卡：6222021234567890123 → 622202**********0123
    "bank_card": lambda v: v[:6] + "**********" + v[-4:] if len(v) >= 13 else "****",
    
    # 邮箱：user@example.com → u***@example.com
    "email": lambda v: v[0] + "***" + v[v.index("@"):] if "@" in v else "***",
    
    # API Key：abcd1234efgh5678 → abcd****5678
    "api_key": lambda v: v[:4] + "****" + v[-4:] if len(v) >= 10 else "****",
    
    # IP地址：192.168.1.100 → 192.168.1.***
    "ip": lambda v: ".".join(v.split(".")[:-1]) + ".***",
}
```

### 4.3 日志脱敏实现

#### 原则一：日志写入时脱敏
```python
# 错误做法：先记录原始值，再后处理
logger.info(f"用户登录: {user}, 密码: {password}")  # ❌

# 正确做法：脱敏后写入
logger.info(f"用户登录: {mask_name(user)}, 密码: {mask_password(password)}")  # ✅
```

#### 原则二：结构化日志 + 统一脱敏层
```python
# 统一脱敏中间件
class SensitiveDataFilter(logging.Filter):
    SENSITIVE_KEYS = {'password', 'token', 'api_key', 'secret', 'bank_card', 'phone'}
    
    def filter(self, record):
        if isinstance(record.msg, dict):
            record.msg = {k: self.mask(k, v) for k, v in record.msg.items()}
        elif isinstance(record.args, dict):
            record.args = {k: self.mask(k, v) for k, v in record.args.items()}
        return True
    
    def mask(self, key, value):
        if key.lower() in self.SENSITIVE_KEYS:
            return "***REDACTED***"
        return value
```

#### 原则三：日志传输和存储安全
- 日志文件权限：600（仅属主可读写）
- 日志目录权限：700
- 日志定期清理（通常保留30-90天）
- 日志服务器访问需审计
- 敏感日志禁止网络传输（走内网或加密通道）

### 4.4 脱敏验证清单

- [ ] 日志中无明文密码
- [ ] 日志中无完整手机号/身份证/银行卡
- [ ] 日志中无完整API Key或Token
- [ ] 日志中无用户完整姓名（应保留姓氏）
- [ ] 异常日志不包含业务敏感数据（如报价、合同金额）
- [ ] 第三方日志服务（ELK/Splunk）配置了脱敏规则
- [ ] 数据库慢查询日志不含敏感字段

## 新增：应急响应流程

### 5.1 事件分级

| 级别 | 名称 | 描述 | 响应时间 |
|-----|------|------|---------|
| P0 | 严重 | 数据泄露（用户信息/支付数据）、服务器被入侵、勒索软件 | 15分钟内 |
| P1 | 高危 | 账户被盗、API被盗用、潜在数据泄露、大规模DDoS | 1小时内 |
| P2 | 中危 | 单个账户异常、接口被刷、钓鱼攻击 | 4小时内 |
| P3 | 低危 | 可疑登录、配置错误、潜在漏洞 | 24小时内 |

### 5.2 应急响应流程（PDCER）

```

│  - 建立安全事件响应团队（技术+法务+管理层）                      │

│  - 储备应急工具（备份介质、取证工具、隔离环境）                   │
│  - 定期演练                                                   │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│  2. Detection & Analysis（检测与分析）                         │
│  - 告警触发：监控告警/用户报告/外部通知                          │
│  - 初步判定：事件真实性、影响范围、严重程度                       │
│  - 取证保留：记录时间线、保存相关日志（防篡改）                    │

                            ↓

│  - 隔离影响：断网/隔离虚拟机/停止相关服务                        │
│  - 证据固定：截屏/抓包/镜像硬盘（用于事后分析或报案）              │

                            ↓

│  4. Eradication（根除）                                       │
│  - 清除威胁：删除恶意文件/后门/恶意代码                          │
│  - 修补漏洞：确认入侵路径，修复漏洞                              │
│  - 重置凭证：所有可能泄露的密码/密钥/Token全部更换                │
│  - 全面扫描：确保无残留                                        │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│  5. Recovery（恢复）                                          │
│  - 从干净备份恢复数据/系统                                     │
│  - 逐步恢复服务（先非关键，后关键）                              │
│  - 加强监控：扩大告警范围、缩短日志保留                          │
│  - 验证服务：确认业务正常运行                                   │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│  6. Post-Incident（事后复盘）                                 │
│  - 编写事件报告：时间线/影响/根因/修复措施                       │
│  - 根因分析：为何发生/为何未检测到/下次如何预防                   │
│  - 改进措施：更新安全规范/加固系统/培训人员                      │
│  - 归档证据：妥善保存以备合规审计或法律用途                       │
└─────────────────────────────────────────────────────────────┘
```

### 5.3 常见场景应急操作

#### 场景A：账户凭证泄露
```
1. 立即冻结被盗账户
2. 检查账户操作日志，确认损失范围
3. 通知受影响用户，强制重置密码
4. 检查是否有横向移动（其他系统也用了相同密码）
5. 如果是内部人员泄露，启动内部调查
```

#### 场景B：API Key泄露
```
1. 立即在1688/支付宝等平台禁用该Key
2. 排查已发生的异常调用（调取平台侧调用记录）
3. 评估损失：是否产生虚假订单/是否产生资金损失
4. 重新生成Key，更新所有使用处
5. 检查泄露原因：日志暴露/代码仓库泄露/传输被截获
```

#### 场景C：数据库被拖库
```
1. 立即隔离数据库（断网/停止写入）
2. 评估泄露范围（哪些表/多少条/是否含密码）
3. 如果含密码：立即强制全体用户重置密码（密码哈希泄露也需重置）
4. 如果含支付信息：按规定通知用户和监管机构
5. 保留证据后恢复或重建数据库
6. 复盘：如何发生的？备份为何被同时影响？
```

#### 场景D：DDoS攻击
```
1. 确认攻击类型（SYN Flood / UDP Flood / Application Layer）
2. 启用云防护服务（如已接入阿里云DDoS高防）
3. 临时限制IP访问频率
4. 与ISP/云服务商协同清洗流量
5. 攻击结束后加强阈值配置
```

### 5.4 通知与报告

#### 内部通知
- P0/P1：立即电话通知CTO + 技术团队 + 法务
- P2：4小时内邮件通知技术负责人
- P3：纳入周报汇总

#### 外部通知（根据法规要求）
- **个人信息泄露**：72小时内向用户和监管机构报告（《个人信息保护法》要求）
- **支付信息泄露**：立即通知支付机构+用户
- **刑事风险（黑客入侵）**：考虑向公安机关报案

#### 对用户通知
- 说明事件情况（不说细节，避免二次伤害）
- 告知已采取的措施
- 告知用户需要做什么（改密码/检查账单等）
- 提供客服联系方式

### 快速检查项目

| 检查项 | 通过标准 |
|-------|---------|
| 凭证存储 | 无硬编码，无明文日志，存环境变量或KMS |
| 1688 API调用 | 签名正确，token安全存储，限速合规 |
| 支付回调 | 签名验证，金额校验，幂等处理 |
| 日志脱敏 | 无密码/手机号/身份证/银行卡/完整Token |
| 反爬合规 | robots.txt，限速，不绕过验证，不抓个人信息 |
| 应急响应 | 有预案，有联系人，有演练记录 |
| 敏感数据访问 | 有审计，有权限控制，有告警 |
| 密码策略 | 复杂度要求，泄露检测，禁止弱密码 |
