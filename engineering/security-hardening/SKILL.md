# Security Hardening

## Overview

安全不是事后检查，是从设计阶段开始的系统工程。OWASP Top 10覆盖了绝大多数常见漏洞，但每个系统有自己独特的攻击面。

## When to Use

- 任何涉及用户认证的功能
- 任何涉及权限控制的功能
- 任何涉及敏感数据的存储或传输
- 任何涉及外部输入的功能
- 上线前的安全检查
- 发现安全漏洞后的修复

## Process

### Phase 1: 威胁建模

#### 1.1 识别资产
- 什么是需要保护的？（用户数据、支付信息、API密钥、业务逻辑）
- 什么被公开暴露？（API、用户界面、管理后台）

#### 1.2 识别攻击面
- 数据入口点？（用户输入、文件上传、第三方API）
- 数据存储点？（数据库、文件系统、缓存）
- 认证机制？（用户名密码、OAuth、API Key、Session）

#### 1.3 识别威胁
- 谁可能攻击？（外部攻击者、恶意用户、内部人员）
- 攻击动机？（数据窃取、权限提升、服务中断）
- 攻击方式？（SQL注入、XSS、CSRF、社会工程）

### Phase 2: OWASP Top 10 检查

#### 2.1 A01: Broken Access Control
- 用户能否访问不该访问的数据？
- 水平越权：用户A能否访问用户B的数据？
- 垂直越权：普通用户能否访问管理员功能？
- IDOR：使用直接对象引用时是否验证权限？

#### 2.2 A02: Cryptographic Failures
- 敏感数据是否加密存储？
- 传输层是否使用TLS？
- 密码是否用强哈希算法（bcrypt/argon2）？
- 密钥是否硬编码在代码中？

#### 2.3 A03: Injection
- 用户输入是否经过验证和清洗？
- SQL查询是否使用参数化查询？
- OS命令是否允许用户输入？
- 文件路径是否验证？

#### 2.4 A04: Insecure Design
- 是否有速率限制（防止暴力破解）？
- 是否有账户锁定机制？
- 是否有完整的日志记录？
- 错误信息是否泄露敏感信息？

#### 2.5 A05: Security Misconfiguration
- 默认凭据是否更改？
- 不必要的服务是否关闭？
- 错误处理是否安全？
- 安全头是否配置？

#### 2.6 A06: Vulnerable Components
- 第三方库是否最新版本？
- 是否有已知漏洞的依赖？
- 组件来源是否可信？
- 是否使用不维护的组件？

#### 2.7 A07: Authentication Failures
- 密码强度要求是否合理？
- 会话ID是否随机且安全生成？
- 会话过期机制是否正确？
- 多因素认证是否可用？

#### 2.8 A08: Software and Data Integrity
- 第三方CDN/库是否验证hash？
- CI/CD流程是否安全？
- 代码来源是否可信？
- 部署包是否验证完整性？

#### 2.9 A09: Security Logging
- 认证事件是否记录？
- 访问控制失败是否记录？
- 日志是否包含敏感信息？
- 日志是否防篡改？

#### 2.10 A10: SSRF
- 用户提供的URL是否验证？
- 是否限制可访问的内网地址？
- 是否有白名单机制？
- 错误信息是否泄露内网信息？

### Phase 3: 安全测试

#### 3.1 自动化扫描
- 使用SAST工具扫描代码
- 使用DAST工具扫描运行应用
- 使用依赖检查工具（OWASP Dependency-Check）

#### 3.2 手动渗透测试
- 关键功能的手动测试
- API接口的越权测试
- 社会工程学测试（钓鱼邮件模拟）

#### 3.3 代码审计
- 敏感函数的代码审查
- 认证授权逻辑的代码审查
- 加密实现的代码审查

### Phase 4: 修复与验证

#### 4.1 修复优先级
- 按风险等级排序
- 高风险立即修复
- 中风险本周修复
- 低风险下个版本修复

#### 4.2 修复验证
- 修复后重新扫描
- 验证漏洞不再存在
- 记录修复方式

## Common Rationalizations

| 常见借口 | 真相 | 反制 |
|---------|------|------|
| "这是内网系统，不需要安全" | 内网也会被攻击，而且攻击后影响更大 | 零信任原则：默认不信任任何网络 |
| "我们太小，没人攻击" | 小公司更容易成为目标，因为攻击成本低 | 记录行业安全事件作为参考 |
| "用了HTTPS就安全了" | HTTPS只加密传输层，应用层漏洞依然存在 | 完整的安全架构检查 |
| "用户密码加密了就行" | 加密不等于哈希，弱加密可被逆向 | 使用bcrypt/argon2等专业密码哈希 |
| "第三方库是开源的，应该安全" | 开源组件有已知漏洞是常态 | 定期更新依赖，使用依赖检查工具 |

## Red Flags

- 任何用户输入不经过验证直接使用
- 任何敏感信息明文存储或传输
- 任何硬编码的密码或密钥
- 任何绕过认证/授权的代码
- 任何SQL拼接用户输入
- 任何文件路径使用用户输入拼接
- 任何错误信息泄露内部结构
