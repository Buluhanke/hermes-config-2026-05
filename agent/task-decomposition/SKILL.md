# Task Decomposition Skill

## 1. 为什么分解是核心能力

复杂任务的失效率与步骤数量呈指数级关系。未分解的任务在执行中段时无法恢复，只能推倒重来。分解将不确定性从"全局混沌"转化为"局部可管理风险"。

- **可追踪**: 每个原子步骤可独立验证进度
- **可回退**: 失败时从最近成功的检查点恢复，而非从头开始
- **可并行**: 无依赖的步骤可同时执行
- **可复用**: 标准化原子步骤可在不同工作流中组合
- **可调试**: 明确知道哪一步出错，而非笼统的"任务失败"

## 2. 分解原则

### 2.1 单一输入输出 (Single Input/Output)

每个步骤有且只有一个明确的输入和一个明确的输出。

```
❌ 不好: "登录并询价" (两个动作)
✅ 好: Step 1 "输入账号密码并登录" → 输出"已登录的session"
    Step 2 "携带session访问询价页" → 输出"询价表单"
```

### 2.2 可验证 (Verifiable)

每个步骤完成后必须有一个可立即检查的判定条件。

```
步骤3: 提交询价
验证条件: 页面出现"询价已提交"文案 或 返回200状态码 且 订单号生成
```

### 2.3 可回退 (Rollbackable)

每个步骤失败后必须有已定义的恢复路径。

```
步骤3失败: 回退到步骤2的状态（询价表单已填充，未提交）
清理动作: 清除已填表单数据，重新渲染页面
```

## 3. 分解模板和示例

### 3.1 标准模板

```
### Step N: [动作描述]
**输入**: [前置数据/状态]
**动作**: [具体操作]
**输出**: [可观测结果]
**验证**: [成功的判定条件]
**失败分支**: [S3A - 描述 | S3B - 描述]
```

### 3.2 模板示例

```
### Step 3: 提交询价表单
**输入**: 已填充的询价表单数据 + 有效session
**动作**: 点击提交按钮，等待网络响应
**输出**: 后端返回询价单号 + 页面跳转至确认页
**验证**: 
  - 响应状态码 = 200
  - 响应体包含 inquiryId 字段
  - DOM出现"提交成功"提示
**失败分支**:
  - S3A: 网络超时 → 重试1次，仍失败则进入S3B
  - S3B: 业务错误(如库存不足) → 提取错误文案，终止流程并输出错误
```

---

## 4. 异常分支处理

异常分支编号规则: `S{N}{字母}`

- `S3A`: Step 3 的第一个异常分支 (通常是可恢复错误)
- `S3B`: Step 3 的第二个异常分支 (通常是硬终止错误)

### 4.1 分支处理流程

```
Step N 执行
    ↓
成功? → YES → 进入 Step N+1
    ↓ NO
分支判断
    ↓         ↓
  SNA        SNB
(可恢复)    (不可恢复)
    ↓         ↓
重试/跳过   记录错误
    ↓         ↓
成功?       终止流程
  ↓   ↓    输出完整
 YES  NO   错误上下文
```

### 4.2 常见异常类型

| 异常码 | 类型 | 处理策略 |
|--------|------|----------|
| S2A | 元素未找到 | 等待 + 重试 (最多3次) |
| S2B | 元素可见但不可交互 | 滚动到可视区 + 重试 |
| S3A | 网络超时 | 重试1次，仍失败则S3B |
| S3B | 业务逻辑错误 | 提取错误信息，终止 |
| S4A | 页面结构变更 | 截图 + 输出DOM快照，终止 |

## 5. 1688场景分解示例 (6步询价流程)

### Step 1: 打开商品详情页
**输入**: 商品ID 或 商品URL
**动作**: 导航至商品详情页，等待页面加载完成
**输出**: 商品标题、价格区间、起订量、主图
**验证**: 
  - 商品标题元素可见
  - 价格元素包含数字
**失败分支**:
  - S1A: 商品不存在/已下架 → 输出"商品不可用"，终止

---

### Step 2: 提取SKU列表
**输入**: Step 1 输出的商品页面
**动作**: 解析SKU选择器，提取所有可选规格组合
**输出**: SKU数组 `[{id, name, price, moq}]`
**验证**: SKU数组长度 > 0
**失败分支**:
  - S2A: 无SKU元素(如仅单规格) → 使用默认规格，继续Step 3
  - S2B: SKU解析失败 → 截图 + 终止

---

### Step 3: 选择目标SKU
**输入**: Step 2 输出的SKU数组 + 用户指定的SKU条件
**动作**: 根据条件匹配SKU，点击对应的规格选择器
**输出**: 已选中的SKU规格 + 对应价格和库存状态
**验证**: 
  - URL参数包含选中的SKU ID
  - 价格元素更新为选中SKU的价格
**失败分支**:
  - S3A: 目标SKU无库存 → 输出"缺货"，询问是否选其他
  - S3B: 规格选择器点击无响应 → 重试1次，仍失败截图终止

---

### Step 4: 填写询价数量
**输入**: Step 3 输出的已选SKU + 目标询价数量
**动作**: 在数量输入框填入数值，校验是否满足MOQ
**输出**: 数量输入框显示目标数值 + 表单校验结果
**验证**: 数量输入框的value等于目标值 且 无MOQ警告
**失败分支**:
  - S4A: 数量低于MOQ → 自动提示用户，终止
  - S4B: 输入框不可编辑 → 检查是否需要先登录

---

### Step 5: 提交询价
**输入**: Step 4 输出的已填表单 + 有效登录session
**动作**: 点击"立即询价"按钮，等待后端响应
**输出**: 询价单号 inquiryId + 确认页
**验证**:
  - 响应状态码 = 200
  - 响应体含 inquiryId (字符串，长度>0)
  - 页面出现"询价成功"文案
**失败分支**:
  - S5A: 未登录被重定向 → 跳转登录页，终止
  - S5B: 后端返回业务错误 → 提取错误文案，终止
  - S5C: 网络超时 → 重试1次，仍失败则终止

---

### Step 6: 确认询价结果
**输入**: Step 5 输出的inquiryId
**动作**: 提取询价单详情(供应商信息、报价时效、联系方式)
**输出**: 结构化的询价结果 `{$inquiryId, supplier, validUntil, contacts}`
**验证**: inquiryId非空 + 至少一个联系方式
**失败分支**:
  - S6A: 页面加载超时 → 根据inquiryId手动查询，终止
  - S6B: 详情页结构变更 → 截图 + 输出原始HTML片段

## 6. 与 n8n 的结合

### 6.1 工作流映射

每个分解步骤对应 n8n 中的一个 Node：

```
┌─────────┐    ┌──────────┐    ┌─────────┐    ┌─────────────┐
│ Trigger │───▶│  Step 1  │───▶│ Step 2  │───▶│   Step 3    │
│  (手动   │    │ HTTP     │    │ HTTP    │    │ Code (分支)  │
│  /Webhook)│   │ Request  │    │ Request │    │ Switch      │
└─────────┘    └──────────┘    └─────────┘    └──────┬──────┘
                                                     │
                              ┌──────────────────────┼──────────────────────┐
                              ▼                      ▼                      ▼
                        ┌──────────┐          ┌──────────┐          ┌──────────┐
                        │  S3A分支  │          │  S3B分支  │          │  成功分支 │
                        │ (重试)    │          │ (终止)    │          │          │
                        └────┬─────┘          └────┬─────┘          └────┬─────┘
                             │                    │                      │
                             ▼                    ▼                      ▼
                        重试Node             Error Node             Step 4
```

### 6.2 状态持久化

在 n8n 中使用 `Set node` + `Wait` 或外部 Redis 存储检查点：

```json
{
  "workflowId": "inquiry-1688-001",
  "currentStep": 3,
  "step2Output": { "skuList": [...] },
  "step3Output": { "selectedSku": {...} },
  "errorHistory": [
    { "step": 3, "branch": "S3A", "attempt": 1, "error": "timeout" }
  ]
}
```

### 6.3 错误处理集成

```
n8n Error Trigger ──▶ 错误分类 Node
                        │
           ┌────────────┼────────────┐
           ▼            ▼            ▼
      可恢复错误     业务错误      系统错误
      (重试workflow) (通知+记录)  (告警+人工介入)
```

### 6.4 子工作流复用

将通用原子步骤封装为独立 n8n Subworkflow：

- `subworkflow-sku-extract`: 提取SKU
- `subworkflow-session-login`: 登录维护session
- `subworkflow-form-submit`: 通用表单提交

主工作流通过 `Execute Workflow` 节点调用子工作流，实现步骤级复用。
