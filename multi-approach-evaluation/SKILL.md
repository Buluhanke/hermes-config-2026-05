# 多方案对比评估工作流

## 触发场景
- 用户说"以这个为基础，全网找找有什么更优的方案""对比几种方法""有没有更好的做法"
- 你提出多个候选方案后，用户表示"建议有点多，我有点不知所措"
- 任何需要从 ≥2 个候选方法中选出/对比的情况

## 核心规则（来自用户直接纠正）
> "你给的建议有点多感觉都很好，我有点不知所措，当然 skill 和能力你先备份一下，然后再去逐步按你刚说的新方案一个个去试试，好几套方案再来对比汇总"

**不要**把方案列表作为选择题抛回给用户（"你选哪个？A/B/C"）。
**要**按以下顺序自主推进：

### Step 1：先备份当前可用产物
在试任何新方案前，先把当前能用的 skill / 脚本 / 配置备份一份（如 `backup-<时间戳>/` 目录）。这样新方案试崩了也能回滚，用户无损失。

### Step 2：按序逐个实测，不跳过、不并行抢答
- 默认按"潜在最优 → 最省事 → 待确认"的顺序，一个个试
- **用户若说"都要，但从 X 开始"**：尊重他指定的子集与起始顺序（如"都要，但从 bc 开始"= 先 B 后 C，A 最后或略过），不要擅自重排成自己认为的"最优序"。用户的部分排序指令优先于 agent 的内部优先级。
- 每个方案给出：**可行性结论 + 实测证据（报错/返回片段）+ 根因**
- 卡住就记"不可行"并说明根因，继续下一个，**不要把卡住的方案伪装成可行**
- 需要用户操作才能继续的（装扩展、装第三方依赖、确认安全），标"待用户确认"并继续能自主的部分

### Step 3：末了给对比汇总表
所有方案试完后，输出一张表：方案 / 可行性 / 速度 / 副作用 / 依赖 / 推荐度。
再给"下一步三选一"式收尾（可含"都要"），让用户一眼决策。

## 反模式（不要做）
- ❌ 方案刚列完就问"你选哪个"——用户会不知所措
- ❌ 只试了一个就下"最优"结论——没对比
- ❌ 把死路包装成"推荐方案"——实测失败的要标不可行+根因
- ❌ 试新方案前不备份——试崩了无法回滚

## 与零反问铁律的关系
本 skill 是"零反问铁律"在**多选项情境**下的具体化：即使有多个好方案，也不把选择负担丢给用户，而是自己排好顺序、逐个验证、最后汇总，让用户做"一眼决策"而非"艰难二选一"。
