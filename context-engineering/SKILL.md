# Context Engineering

## Overview

上下文是AI完成任务的核心资源。上下文管理不当会导致：重复工作、方向偏离、遗漏关键信息、错误决策。

上下文工程的目标：在任何时刻，都确保当前上下文中包含且仅包含完成任务所需的信息。

## When to Use

- 任何预计超过30分钟的连续任务
- 任何需要跨越多个会话/对话继续的任务
- 任何多人协作的任务交接
- 任何发现"上下文丢失"或"假设错误"的时刻
- 任何需要决定"现在上下文够不够"的时候

## Process

### Phase 1: 上下文盘点（开始任务时）

#### 1.1 识别必需上下文
- 任务目标是什么？（一句话）
- 前置条件是什么？（已有什么？需要什么？）
- 关键约束是什么？（不能做什么？）
- 验收标准是什么？（怎么算完成？）

#### 1.2 评估当前上下文
- 上述信息是否都在当前上下文中？
- 哪些缺失？需要补充什么？
- 哪些冗余？会分散注意力？

#### 1.3 检查历史上下文
- 这个任务之前有做过吗？
- 之前的上下文和现在一致吗？
- 之前有什么决策/假设需要延续？

### Phase 2: 上下文组织（执行任务中）

#### 2.1 保持上下文精简
- 只保留当前步骤相关的文件/代码在上下文中
- 用完就清理，不要积累
- 把已完成的步骤从"当前任务"移到"已完成记录"

#### 2.2 建立上下文锚点
- 在长任务中，每完成一个里程碑就记录上下文快照
- 记录：当前目标、已完成、未完成、关键决策
- 格式：简短、有条理、能在1分钟内回顾

#### 2.3 追踪信息源
- 每个关键信息标注来源（文档/代码/对话/推测）
- 区分：已知事实 vs 假设 vs 推测
- 不确定的信息要明确标注

### Phase 3: 上下文传递（交接时）

#### 3.1 编写交接文档
- 任务背景（为什么做这件事）
- 当前状态（已完成、未完成、进行中）
- 关键决策（做了哪些决定，为什么）
- 风险和已知问题
- 下一步行动（具体、可执行）

#### 3.2 验证交接完整性
- 交接文档能否让接手的人在30分钟内上手？
- 是否有遗漏的关键信息？
- 接手的人是否有问题清单？

#### 3.3 上下文压缩
- 长任务交接前压缩上下文
- 只保留核心信息和关键引用
- 把详细日志/对话归档到外部

### Phase 4: 上下文维护（持续）

#### 4.1 定期回顾
- 每完成一个子任务就回顾整体目标
- 检查当前上下文是否还在正确的方向上
- 问：现在的上下文是否仍然满足任务需求？

#### 4.2 处理上下文溢出
- 当上下文快满时，优先保留：任务目标、当前步骤、关键决策
- 可以丢弃：详细日志、已验证的错误信息、已废弃的方案
- 不确定时就问：这段信息对完成任务是否必需？

#### 4.3 上下文归档
- 完成后整理本次任务的上下文记录
- 归档到知识库/文档系统
- 记录经验教训（what worked, what didn't）

## Common Rationalizations

| 常见借口 | 真相 | 反制 |
|---------|------|------|
| "上下文够了，不用整理" | 上下文够不够是由任务需求决定，不是由感觉决定 | 明确列出"必需上下文清单"并逐项核对 |
| "这段信息可能以后有用" | 上下文中的冗余信息会稀释关键信息 | 只有当前和下一步必需的信息才保留 |
| "上下文管理是overhead" | 好的上下文管理减少至少50%的重复工作 | 记录因上下文问题浪费的时间 |
| "我可以记住所有细节" | 人的记忆不可靠，尤其是在长任务中 | 把关键信息写下来，而不是依赖记忆 |
| "交接太麻烦，先继续干" | 没有完整交接的任务无法被其他人接手 | 把交接当成任务的一部分，不是额外工作 |

## Red Flags

- 发现自己在重复问同一个问题
- 不知道当前任务进行到哪里了
- 突然意识到之前有个关键假设可能是错的
- 无法解释为什么在做当前这个步骤
- 上下文窗口已经用了80%以上
- 有多个相关信息但不知道该信哪个
- 任务交接后接手的人需要从头问很多问题

## Verification

验证清单：

- [ ] 任务目标在当前上下文中明确可见
- [ ] 已识别并记录所有关键假设
- [ ] 当前步骤和整体目标的关系清晰
- [ ] 交接文档能让接手者快速上手
- [ ] 不需要的信息已从上下文中清除
- [ ] 重要决策和其理由已记录
- [ ] 任务完成后有完整的归档记录
