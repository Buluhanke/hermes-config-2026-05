# Tool Stack Evolution — 工具栈进化方法论

**任何对当下技术栈的"小修小补"之前，先问一句：当下方案是不是全网最强的免费替代品？**

## 核心区分：修补 vs 进化

| 行为 | 修补 | 进化 |
|------|------|------|
| 看到 searxng 后端空 | 写 fetch_url 替代它 | **先问"当下最强免费方案是什么"**，全网搜（`web_search "best free <类> 2026"`），找到 Trafilatura 替换整个提取器层 |
| 发现缓存慢 | 加 in-memory dict 优化 | 搜全网缓存库（diskcache/cachetools/fakeredis），用 DiskCache 替换 |
| 浏览器抓页面被反爬 | 加更复杂的 User-Agent 轮换 | 评估 Playwright/Selenium/Camofox/Jina Reader/Crawl4AI，找最强的换 |
| 自动化 GUI 操作不稳 | 调坐标偏移参数 | 评估 Peekaboo/CuaDriver/OpenClaw Computer Use 等方案，挑最强的换 |
| 触发条件 | 用户说"修个 bug"/"X 行小修" | 用户说"升级"/"找更强的"/"全网对比" |

## 进化流程（5 步）

1. **盘点当下栈** — 列出每个位置用什么、有何短板
2. **全网搜索候选** — 每个位置搜 `best free <类> 2026`，3-5 个候选
3. **本机实测筛选** — 必须能在这台机器跑（不是 GitHub 上 stars 多就选，要 curl 实测连得通）
4. **对比决策表** — 候选 × 维度（成本/质量/维护/兼容性），1-2 个赢家
5. **替换而非叠加** — 写新代码替换旧代码，不是在旧代码上 patch

## 实测筛选规则（本机优先）

**GitHub 上 star 多 ≠ 能用**。每个候选必须跑：

```bash
# 1. 安装/拉取
# 2. 写一个最小测试，跑真实场景
# 3. 拿真实输出对比质量
# 4. 排除条件：DNS 解析失败、连接超时、需付费 key 才有完整功能
```

**排除清单必须公开**（写进 memory 或 skill 维护记录），下次不要重测：

## 铁律

> **用户拍板（2026-06-07 04:20 原话）**：
> "先用当下的再去全网搜罗比当下更强的更好的也是免费的来替换当下的方案才是进化，
> 而不是在当下的情况不停地找错，这个不是进化，这是修补。"

**反模式（不要做）**：

- ❌ 看到当下方案有问题就直接打补丁——**先全网搜 "best free X 2026" 对比，再决定替换**
- ❌ 只在用户说"升级"时才走这流程——任何"X 不好用""X 不稳""X 慢"的反馈都是触发信号
- ❌ 装新东西覆盖旧东西而不是替换——会导致依赖爆炸 + 维护噩梦
- ❌ 不实测就信"GitHub 上 star 多"——stars 不是质量证书，本机跑通才是

## 触发词速查

| 你听到/看到 | 走哪条路 |
|---|---|
| "X 不好用" / "X 慢" / "X 不稳" | **修补**（单点修） |
| "升级 X" / "找更强的" / "全网对比" | **进化**（走本 skill 5 步） |
| "X 行小修" / "顺手修" | **scope 边界**——不一定走进化，先问用户 |
| "装 Y" / "用 Z 替代" | **可能进化**——先盘点当下栈再决定 |
